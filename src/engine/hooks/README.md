# `hooks/`: hand-written card logic

Most cards are fully described by data (`behavior`, `action`, `requirements`) and are run by
the generic interpreter in `behavior/`. This package holds the cards that data can't express:
the 446 cards whose original TypeScript overrides one or more methods. Each of those methods
is a **hook**, and every hook is written here by hand.

Progress is tracked in [`STATUS.md`](STATUS.md), which is generated. Don't edit it.

| Read this | For |
| --- | --- |
| [`STATUS.md`](STATUS.md) | What's done, what's missing, what's tested |
| `data/reference/hooks_reference.md` | What each hook means and when the game calls it |
| `data/reference/behavior_spec.md` | How the data-driven part works (so you know what *not* to rewrite) |

---

## 1. Layout

```
hooks/
  README.md        this file
  STATUS.md        generated by tools/hook_status.py
  registry.py      the @hook decorator and the HOOKS dict
  __init__.py      imports every module below so registration runs
  base.py          one module per expansion, named after the card's `module` field
  prelude.py
  moon.py
  underworld.py
  ...
```

Put a card in the file that matches its `module` in the card JSON. That's also the Module
column in the tracker spreadsheet, so you can finish one expansion at a time.

## 2. Adding a hook

1. Find the card in `STATUS.md` (or run `python tools/hook_status.py --module moon`) to see
   which hooks it needs.
2. Open the matching module file and register one function per hook.
3. Add the module to `__init__.py` if it's new.
4. Write a test (section 6).
5. Run `python tools/hook_status.py --check`. It should report no errors.

```python
# hooks/prelude.py
from .registry import hook

@hook("ECCENTRIC_SPONSOR", name="bespoke_play")
def sponsor_play(state, owner):
    """Eccentric Sponsor (P11): play a card from hand with a 25 M€ discount.

    Original: prelude/EccentricSponsor.ts  (bespokePlay, getCardDiscount)
    Asks:     play_card -> "sponsor.done"
    Fizzles:  if no card is played (rule: the prelude is lost)
    Diverges: the discount is passed to play_card instead of a lastCardPlayed flag.
    """
    ...
```

(The helpers used inside hooks, such as `ask`, `play_card` and `fizzle`, live in
`engine/primitives.py` and `engine/pending.py`.)

A single function can serve several cards. Variants such as the Ares versions share logic
with their base card, and the decorator takes any number of IDs:

```python
@hook("ECOLOGICAL_ZONE", "ECOLOGICAL_ZONE_ARES", name="on_card_played")
def ecological_zone_card_played(state, owner, card): ...
```

### Hook names

The Python name is the original TypeScript name in snake_case: `bespokePlay` becomes
`bespoke_play`, `onTilePlaced` becomes `on_tile_placed`. The registry rejects duplicates, so
defining the same hook for the same card twice raises an error at import time.

### Hooks you decide not to need

Sometimes your design makes a hook unnecessary. Eccentric Sponsor's `getCardDiscount` only
exists in the original because it uses a `lastCardPlayed` flag. Don't leave it out silently.
Register a trivial version and record why, so the status page stays honest and the decision
is visible:

```python
@hook("ECCENTRIC_SPONSOR", name="get_card_discount")
def sponsor_discount(state, owner, card):
    """Diverges: always 0. The 25 M€ is passed explicitly by sponsor_play."""
    return 0
```

## 3. Signatures

These are the proposed Python signatures, derived from the TypeScript ones. `state` is the
current game state, and `owner` is the player who owns the card.

| Kind | Rule | Returns |
| --- | --- | --- |
| **Query** (`can_*`, `get_*`, `gains_from_tile_placement`, `production_box`) | Must **not** change anything | A value |
| **Effect** (`bespoke_play*`, `play`, `action`, `action_essence`, `initial_action`) | Changes the game | A new state |
| **Trigger** (`on_*`) | Reacts to an event | A new state |

Queries run constantly (to build the legal-action list and to evaluate positions), so keep
them fast and free of side effects.

| Hook | Arguments after `state, owner` | Returns |
| --- | --- | --- |
| `bespoke_play`, `bespoke_play_before`, `play` | none | state |
| `bespoke_can_play`, `can_play`, `bespoke_can_act`, `can_act` | none | bool |
| `action`, `action_essence`, `initial_action` | none | state |
| `on_card_played` | `card` | state |
| `on_card_played_by_any_player` | `card, active_player` | state |
| `on_tile_placed` | `active_player, space, board_type` | state |
| `on_non_card_tag_added`, `on_non_card_tag_added_by_any_player` | `tag` | state |
| `on_science_tag_added` | `count` | state |
| `on_resource_added` | `card, count` | state |
| `on_increase_terraform_rating_by_any_player` | `player, steps` | state |
| `on_global_parameter_increase` | `parameter, steps` | state |
| `on_production_gain` | `resource, amount` | state |
| `on_production_phase`, `on_discard` | none | state |
| `on_colony_added_by_any_player` | `colony_owner` | state |
| `on_claim` | `is_excavate, space` | state |
| `on_identification_by_any_player` | `identifying_player, token` | state |
| `on_standard_project` | `project` | state |
| `gains_from_tile_placement` | `space, tile_type` | `(stock, production)` |
| `get_card_discount` | `card` | int |
| `get_standard_project_discount` | `project` | int |
| `get_global_parameter_requirement_bonus` | `parameter` | int |
| `can_pay_with` | none | mapping |
| `get_victory_points` | `context="default"` | int |
| `production_box` | none | units |
| `serialize`, `deserialize` | usually not needed | n/a |

`serialize` and `deserialize` exist in the original only to save and restore per-card
fields. If your game state is plain frozen data that you can copy and save directly, you
probably don't need them. If so, register a stub and say so, as described above.

## 4. Rules every hook follows

**Never mutate.** Take a state, return a new one. Use the primitives (`add_stock`,
`add_production`, `raise_global`, `place_tile`, `draw_cards`, ...), which build new states for
you. Don't edit `state` in place, even though it would be shorter.

**Ask, don't pause.** When an effect needs a decision, record a pending choice and return.
The continuation is a string key plus data, never a closure or generator, because a state
that holds a closure can't be copied, hashed or saved:

```python
return ask(state, owner, kind="play_card", options=..., then="sponsor.done")

@continuation("sponsor.done")
def sponsor_done(state, owner, choice): ...
```

**Order is part of the rules.** Triggers run in a fixed, deterministic order, and many
effects in the original are *deferred* to a queue and resolve after the current step. Keep a
card's order of effects the same as the original's, and note it in the docstring when the
order matters.

**Pure queries stay pure.** `can_play` and friends must not log, draw cards, or touch the
random number generator. Randomness belongs in effects, through the seeded RNG stored in the
state.

**Dependencies run one way.** Hooks import from `engine/primitives`, `engine/pending` and
`state`. Those modules never import `hooks`. This is what prevents circular imports.

**Prefer data over code.** Before writing a hook, check whether the card's `behavior` already
covers part of it. The interpreter runs `behavior` first, so a hook should only do the part
the data can't say. Check `behavior_spec.md` for what the interpreter already handles.

## 5. Docstrings and comments

Use the short template for any hook with real logic:

```python
"""<Card name> (<card number>): <one-line summary>.

Original: <path>.ts  (<methods ported>)
Asks:     <pending kind -> continuation key>        # only if it asks
Diverges: <deliberate difference from the original> # leave out if it's a faithful port
"""
```

The `Original:` line matters most. When a test disagrees with the reference engine, it tells
you where to look. An empty `Diverges:` means you are claiming a faithful port, so keep it
accurate. Skip the docstring for trivial hooks (a discount that returns a constant) and use a
one-line comment instead.

Each module file starts with a docstring that says which cards it covers, which TypeScript
folder they came from, and any expansion rules its hooks assume.

## 6. Tests

Put one test file per hook module under `tests/unit/` (for example `test_hooks_moon.py`).
Each test builds a small state, runs the hook, and checks the result.

**Name tests after the card.** The status script counts a card as tested when a test function
is named `test_<card_id_in_lowercase>` or starts with `test_<card_id_in_lowercase>_`:

```python
def test_eccentric_sponsor_fizzles_when_hand_is_empty(): ...
def test_ecological_zone_ares_gains_animal_on_tag(): ...
```

A test is credited to the longest matching card ID, so `test_ecological_zone_ares_...` counts
for `ECOLOGICAL_ZONE_ARES`, not for `ECOLOGICAL_ZONE`.

What this does and doesn't tell you: the "Tested" column means *at least one test is named
after the card*. It doesn't check that the test is any good, or that every hook on the card
is covered. Treat it as a reminder, not a guarantee.

The stronger check is differential testing: run the same seeded game in your engine and the
original TypeScript engine and compare states (`tests/differential/`).

## 7. The status script

```bash
python tools/hook_status.py                     # write STATUS.md and print a summary line
python tools/hook_status.py --check             # also exit 1 if there are errors
python tools/hook_status.py --require-complete  # also exit 1 if any hook is still missing
python tools/hook_status.py --module moon       # list one module's missing hooks; write nothing
```

Run it from the project root. By default it reads `data/cards/*.json`, imports `tmars.hooks`
from `src/`, scans `tests/`, and writes `src/tmars/hooks/STATUS.md`. The paths and package
name can be changed with `--cards`, `--src`, `--hooks-module`, `--tests` and `--out`. It uses
only the standard library, and its output has no timestamps, so version-control diffs show
only real changes.

**How it decides what a card needs.** It reads each card's `methods` field from the JSON and
keeps the names that are known hooks. Helper methods (for example `getAvailableSpaces`) are
ignored. The list of known hooks is `HOOK_KINDS` at the top of the script.

**What it reports**

| Problem | Severity | Meaning |
| --- | --- | --- |
| `unknown-card` | error | Hooks are registered for an ID that isn't a card needing hooks. Usually a typo. It also fires for fully data-driven cards, which need no hooks. |
| `unknown-hook` | error | A registered hook name isn't one of the known hooks (for example `on_card_playd`) |
| `not-required` | warning | The hook name is real, but the original card has no such method |
| missing hook | listed | A needed hook isn't registered yet. This is an error only under `--require-complete`. |

**Suggested CI use.** Run `--check` from the start, so typos fail the build. Switch to
`--require-complete` once the port is meant to be finished.

**What it does not check**

- **Signatures.** It verifies hook *names* and coverage, not the arguments your functions
  accept. A function with the wrong parameters passes until a test or the engine calls it.
- **Correctness.** It can't tell whether a hook behaves like the original.
- **New upstream hooks.** If you regenerate the JSON from a newer version of the original
  repo and a card gains a hook that isn't in `HOOK_KINDS`, the script ignores it. After
  re-running the extractor, check whether any new hook names appeared, and add them to
  `HOOK_KINDS` if so.

## 8. Keeping the data current

`data/cards/*.json` is generated by `tools/extract_cards.py` from the original TypeScript.
Never edit it by hand. If a card's data is wrong, fix the extractor and regenerate, so your
fix survives the next update from the original repo. Then run `hook_status.py`. Any hooks
that appeared or disappeared will show up in `STATUS.md`.
